## 2. "매주 업데이트 해야 하나?" — **아니오. 크론 한 줄이면 끝입니다.**

이게 이번 질문의 핵심인데, 레이어가 두 개로 나뉘어 있어서 헷갈리기 쉽습니다.

### 레이어 1 — 조회 (이미 자동)

`backend/main/views.py:91` 이 요청이 올 때마다 실시간으로 거릅니다.

```python
Festival.objects.filter(is_trash=False).filter(Q(end_date__isnull=True) | Q(end_date__gte=now))
```

`now` 는 매 요청 시각입니다. 그래서 **끝난 행사는 아무도 손대지 않아도 다음 날 자동으로
사라집니다.** 배너도 마찬가지로 `START_DATE`/`END_DATE` 기간 판정이 들어가 있습니다
(`views.py:29 within_period`). 코드나 데이터를 매주 고칠 일은 없습니다.

홈 화면 섹션 제목을 `"이번 주 소식"` 이 아니라 `"경주 소식"` 으로 둔 것도 같은 이유입니다
(`HomeTab.jsx:38` 주석 참고). 제목에 기간을 박으면 사람이 매주 손대야 하는 것처럼
읽히기 때문입니다. **이 판단은 유지하는 걸 권합니다.**

### 레이어 2 — 수집 (크론 필요)

새 행사가 DB 에 들어오려면 `sync_festivals` 가 주기적으로 돌아야 합니다. 이건 사람이
아니라 스케줄러가 합니다.

```cron
# 매일 새벽 4시
0 4 * * * cd /path/to/backend && .venv/bin/python manage.py sync_festivals >> /var/log/sync.log 2>&1
0 5 * * * cd /path/to/backend && .venv/bin/python manage.py sync_places >> /var/log/sync.log 2>&1
```

행사 정보가 하루에 몇 번씩 바뀌는 데이터가 아니라서 일 1회로 충분합니다.
`sync.py` 가 `(SOURCE, CONTENT_ID)` 기준 upsert 라 몇 번을 돌려도 중복이 안 생깁니다.

배포 환경이 정해지면 크론 대신 django-crontab / Celery beat / 클라우드 스케줄러 중
하나를 고르면 되는데, 지금 단계에선 그냥 crontab 이 제일 낫습니다.

**결론: 매주 수동 업데이트는 필요 없습니다. 크론만 걸면 됩니다.**

## 3. 경주시 행사 페이지 링크 연동

### 지금 어떻게 되어 있나

`FESTIVAL.URL` → 프론트 `HomeTab.jsx:116` 의 "행사 정보" 링크로 이미 이어집니다.
값은 TourAPI `detailCommon2` 의 `homepage` 필드에서 옵니다
(`tourapi/mappers.py:114 extract_homepage_url` — HTML `<a>` 태그로 오는 걸 URL 만 뽑아냄).

즉 **배관은 이미 다 깔려 있습니다.** 문제는 어떤 행사를 담느냐입니다.

### 문제

말씀하신 [경주시 행사 페이지](https://www.gyeongju.go.kr/tour/page.do?mnu_uid=2261) 에는
전시·공연이 많습니다. 예시로 주신
`2026 한수원아트페스티벌 특별전` → `garts.kr/...schedId=SCHED_0000021189` 같은 것들요.

그런데 TourAPI 축제 API(`contentTypeId=15`)로 경주에서 나오는 건 **4건뿐**입니다 (1번 참고).
경주시 페이지의 전시·공연은 대부분 TourAPI 에 등록되어 있지 않습니다. 성격이 다릅니다.

- TourAPI = 관광공사가 집계한 "축제"
- 경주시 페이지 = 시가 직접 올리는 전시·공연·행사 전반

### 선택지 (제가 고르지 않고 남겨둡니다 — 프로젝트 요건 판단이 필요합니다)

| 안 | 내용 | 장 | 단 |
| --- | --- | --- | --- |
| A | TourAPI 만 쓴다 | 이미 됨. 공식 API 활용 요건 충족 | 행사 4건뿐, 화면이 빈약함 |
| B | 경주시 페이지 크롤러를 **추가** | 실제 열리는 행사 다 나옴. 링크도 원본 그대로 | 크롤러는 페이지 구조 바뀌면 깨짐. 유지보수 비용 |
| C | 수기 등록 | 정확함 | 사람이 계속 넣어야 함 |

**B 를 권합니다.** 이유:

1. 스키마가 이미 대비되어 있습니다. `(SOURCE, CONTENT_ID)` **복합** UNIQUE 라
   `SOURCE='TOUR_API'` 와 `SOURCE='GYEONGJU_CITY'` 가 같은 테이블에서 충돌 없이 공존합니다.
   이거 때문에 팀과 스키마 협의를 한 번 더 했던 겁니다 (`backend/docs/db/team-reply-2.md`).
2. A(TourAPI)를 **버리는 게 아니라 더하는** 것이라 공사 API 활용 요건이 그대로 유지됩니다.
3. 홈 API(`views.py`)는 `SOURCE` 를 전혀 안 봅니다. 백엔드 조회 코드도, 프론트도
   **한 줄도 안 고쳐도** 됩니다. 수집기만 하나 늘어납니다.

### B 로 갈 경우 작업 항목

- `backend/gyeongju/` 앱 신설 (또는 `tourapi/` 안에 `city.py`)
- 목록 페이지 파싱 → 제목 / 기간 / 장소 / 상세 링크 / 이미지
- `CONTENT_ID` 는 상세 링크에서 안정적인 식별자를 뽑아 쓸 것.
  예시 링크의 `SCHED_0000021189` 처럼 URL 안의 고유 ID 를 쓰면 됩니다.
  **URL 전체를 CONTENT_ID 로 쓰지 마세요** — 쿼리스트링 순서가 바뀌면 중복 적재됩니다.
- `SOURCE='GYEONGJU_CITY'` 로 고정. `core/models.py:16` 옆에 상수 추가
- `FESTIVAL.URL` 에 상세 링크를 그대로 저장 → 프론트가 바로 씀
- `sync.py` 의 upsert 를 재사용할 것. 새로 짜지 마세요
- **파서는 HTTP 없이 테스트할 것.** `tourapi/mappers.py` 를 HTTP 에서 떼어놓은 것과
  같은 이유입니다. 저장해 둔 HTML 픽스처로 테스트하면 페이지가 바뀌어도 테스트가
  먼저 깨져서 알려줍니다
- 크론은 2번의 `sync_festivals` 와 같은 자리에 한 줄 추가. **여기도 매주 수동 아닙니다**

### 같이 봐야 할 것 — 섹션 제목과 필터가 안 맞습니다

홈 섹션 제목은 `"지금 열리는 행사"`(`HomeTab.jsx:46`)인데, 실제 필터는
`"아직 안 끝난 행사"` 입니다. 그래서 10월 신라문화제처럼 **아직 시작 안 한 행사도
"지금 열리는" 자리에 나옵니다.** 둘 중 하나로 맞춰야 합니다.

- 제목을 `"다가오는 행사"` / `"경주 행사"` 로 바꾼다 (코드 1줄, 권장)
- 또는 필터에 `start_date <= now` 를 추가한다 (지금 열리는 것만. 대신 4건이 1건으로 줄어듦)

## 4. 화면에 보이는 가짜 데이터 걷어내기

### 무엇이 가짜인가

`"시스템 점검 안내"` 팝업, `"[테스트] 좌표 깨진 곳"` 추천 관광지, `"경주의 밤"` /
`"벚꽃 시즌"` 배너, `"신라문화제"` / `"번역 없는 축제"` — 화면에 보이는 건 **전부**
`backend/main/management/commands/seed_demo.py` 가 넣은 로컬 시드입니다.

DB 에 데이터가 하나도 없으면 API 가 빈 배열을 내고 화면이 텅 비어서, 연동이 된 건지
안 된 건지 구분이 안 되기 때문에 만들어 둔 것입니다. `DEBUG=0` 에서는 실행이 막혀
있어서 운영 DB 를 오염시키지는 않습니다 (`seed_demo.py:42`).

### 왜 지금 실데이터가 안 나오나

`sync_places` 는 잘 돕니다. 방금 돌려서 실제 경주 관광지가 들어왔습니다:

```
TOUR_API 136208 한화리조트 경주   | is_recommended=False
TOUR_API 128430 옥산 세심마을     | is_recommended=False
TOUR_API 1958111 나산서원        | is_recommended=False
```

그런데 **전부 `is_recommended=False`** 입니다. 추천 관광지 API 는
`filter(is_recommended=True, is_display=True)` 라서(`views.py:115`) 이 행들이 안 잡힙니다.
남는 건 시드가 넣어둔 불국사 / 첨성대 / **[테스트] 좌표 깨진 곳** 셋뿐이고, 그래서
화면에 테스트 행이 보이는 겁니다.

`IS_RECOMMENDED` 는 운영자가 켜는 큐레이션 플래그입니다. 수집기가 임의로 켜면 안 됩니다.

### 해야 할 일

1. **`seed_demo.py` 는 지우지 말 것.** `DEBUG` 가드가 있고, "걸러져야 하는 행이 실제로
   걸러지는가"를 확인하는 유일한 수단입니다 (`backend/docs/verify-checklist.md` 가 이걸 씁니다).
   지워야 할 건 **파일이 아니라 로컬 DB 의 행** 입니다.
2. 로컬 DB 를 실데이터로 갈아끼우기:
   ```bash
   cd backend
   rm db.sqlite3                       # 시드 포함 전부 날림 (gitignore 되어 있음)
   .venv/bin/python manage.py sync_places
   .venv/bin/python manage.py sync_festivals   # 1번 고친 뒤에
   ```
3. **추천 관광지를 어떻게 정할지 결정해야 합니다.** 이건 제품 판단이라 남겨둡니다:
   - (a) 관리자 화면에서 수동으로 켠다 — 원래 의도. 근데 관리자 화면이 아직 없음
   - (b) 초기 큐레이션 목록(불국사·첨성대·대릉원·안압지 등)을 `CONTENT_ID` 로 지정해
         `IS_RECOMMENDED=1` 을 켜는 일회성 커맨드를 만든다 — **현실적으로 이게 낫습니다**
   - (c) `VIEW_COUNT` 상위 N 개를 자동 추천 처리 — 지금은 `VIEW_COUNT` 가 전부 0 이라 무의미
4. 배너(`MAIN_BANNER`)와 팝업(`POPUP`)은 **API 출처가 없습니다.** 운영자가 등록하는
   테이블입니다. 실제로 뭘 띄울지 팀에서 정해야 하고, 정해지기 전까지는 빈 상태
   (`"새로운 공지가 없어요."`)가 정상입니다. 시드 배너 이미지는 `frontend/public` 에
   실제로 있는 파일이라 화면이 깨지지는 않습니다.

| `CONTENT_ID VARCHAR(50)` | 추가 |
| `UNIQUE (SOURCE, CONTENT_ID)` | 추가 |
| `KEY (IS_TRASH, END_DATE)` | 추가 |

**테이블 단위**

| 테이블 | 변경 | 비고 |
| --- | --- | --- |
| `PLACE_I18N` | **신규 생성** | 관광지 다국어. `ADDRESS`/`ADMISSION_FEE` 도 번역 대상 |
| `CATEGORY` | **삭제** | TourAPI `contenttypeid`(39=음식점, 나머지=관광지)로 대체 가능 |
| `CATEGORY_CONTENT_I18N` | **미결** | `PLACE_I18N` 과 역할 중복. **팀 확인 대기 중 — 이거 아직 답 못 받았습니다** |

전체 테이블 수는 **27개 그대로** 입니다 (`CATEGORY` 삭제 −1, `PLACE_I18N` 신규 +1).

`schema-v2.sql` 은 **변경되는 3개 테이블만** 담고 있습니다. 나머지 24개는 원본
`schema.sql` 그대로라 중복해서 넣지 않았습니다. 이 파일은 원본 DDL 의 해당
`CREATE TABLE` 을 갈아끼우는 용도이고, 이미 데이터가 있는 DB 에는 `schema-v2-alter.sql`
을 써야 합니다 (v2 쪽은 DROP 후 재생성이라 데이터가 날아갑니다).

### 같이 고쳐야 할 것 — 설계 문서가 낡았습니다

`docs/superpowers/specs/2026-07-25-main-home-api-design.md` 가 **협의 전 1차 버전** 인
채로 남아 있습니다. 실제 구현과 어긋나는 부분:

| 위치 | 문서 내용 | 실제 |
| --- | --- | --- |
| §4 모델 표 | `CATEGORY` / `Category` 가 있음 | 삭제됨. `PLACE.TYPE` 로 대체 |
| §5 추천 관광지 | "`PLACE_I18N` 이 DDL 에 없으므로 `?lang=` 은 무시한다" | `PLACE_I18N` 생겼고 번역 **동작함** |
| §5 | "`CATEGORY_CONTENT_I18N` … 확인 전까지 조인하지 않는다" | 여전히 미결이나, 이유가 바뀜 |
| §8 스키마 보완 요청 | 단일 `CONTENT_ID` UNIQUE 제안 | `(SOURCE, CONTENT_ID)` 복합으로 확정 |

## 7. "제대로 한 게 맞나" 체크 — 검증된 것과 안 된 것

정직하게 나눕니다.

### 실행해서 확인한 것 ✅

- 백엔드 테스트 112개 통과 (`manage.py test`)
- 프론트 테스트 73개 통과 (`npm test`)
- TourAPI 인증키 유효 — `sync_places` 로 실제 경주 관광지 3건 적재됨
- `searchFestival2` 파라미터 문제 — 위 1번 표는 전부 실제 API 응답입니다
- gitignore 가 `.env` / `db.sqlite3` / `.venv` 를 막고 있음

### 확인 안 된 것 ⚠️ — Gemini 가 해야 할 검증

1. **MySQL 연결.** `DB_NAME` 이 비어 있어 지금까지 SQLite 로만 돌았습니다.
   `managed=False` 모델이 팀의 실제 대문자 테이블/컬럼과 맞는지는 **MySQL 에 붙여봐야
   압니다.** SQLite 테스트는 모델 정의로 테이블을 만들기 때문에 오타가 있어도 통과합니다.
   → 팀 DB 접속 정보 받아서 `.env` 채우고 `manage.py shell` 에서
   `Place.objects.count()` 정도만 쳐보면 바로 판명됩니다. **이게 제일 큰 미검증 항목입니다.**
2. **프론트 + 백엔드 동시 구동 화면.** 각각의 테스트는 통과하지만 실제로 두 서버를
   띄워서 홈 화면을 눈으로 본 적이 없습니다. CORS, 필드명 불일치 같은 건 여기서 나옵니다.
   → `backend/docs/verify-checklist.md` 의 5번 항목
   → **주의: 이 PC 의 8000 포트는 다른 프로세스가 쓰고 있습니다.** `runserver 8123`
     같은 빈 포트를 쓰고 `frontend/.env.local` 의 `NEXT_PUBLIC_API_BASE_URL` 도 맞추세요
3. **축제 수집 실데이터.** 1번을 고친 뒤에야 확인 가능합니다
4. **다국어 실데이터.** `PLACE_I18N` / `FESTIVAL_I18N` 에 실제 번역을 넣어본 적이
   없습니다. 수집기는 한국어만 넣습니다. 번역을 누가 채울지 정해진 게 없습니다
5. **`?lang=en` 이 화면에 반영되는지.** `PlayGyeongju.jsx:96` 에서 `user.language` 를
   내려주게 해뒀는데, 실제로 언어를 바꿔서 확인한 적이 없습니다

### 의도적으로 안 한 것 (되돌리지 마세요)

- **폴백 데이터 없음.** API 가 죽으면 하드코딩된 가짜 데이터를 보여주지 않고 에러
  상태를 냅니다 (`useApiResource.js:9` 주석). 죽은 백엔드가 정상 화면인 척하면
  디버깅이 불가능해집니다
- **`django.contrib.admin` 안 씀.** `INSTALLED_APPS` 를 최소로 유지해서 `migrate` 가
  팀 MySQL 에 `auth_*`, `django_content_type` 테이블을 만들지 않게 했습니다.
  관리자 화면이 필요하면 이 결정을 팀과 상의한 뒤에 되돌리세요
- **캐싱 없음.** 트래픽 특성을 모르는 상태에서 넣지 않았습니다
