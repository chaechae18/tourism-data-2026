# 퀘스트 아이템 보상

역할별로 새 퀘스트를 완료할 때 `모자 → 상의 → 하의 → 손 아이템 → 배경` 순서로 하나씩 지급한다. 목록의 방문 순서가 아니라 실제 완료 순서를 사용한다. 역할을 바꿔도 각 역할의 보유 아이템과 착용 상태가 유지된다.

- 기존에 보상 없이 완료한 퀘스트는 다시 지급하지 않는다. 다음 새 퀘스트를 완료할 때 아직 받지 않은 첫 아이템부터 지급한다.
- 같은 퀘스트 재요청은 완료 시각을 유지하며 추가 지급하지 않는다. 다섯 아이템을 받은 역할은 코스를 새로 만들어도 중복 지급하지 않는다.
- GPS 방문과 시연 완료는 같은 저장·보상 경로를 사용한다. 다른 사용자의 퀘스트는 완료할 수 없다.
- `USER_CHARACTER` 행 잠금으로 동시 요청을 직렬화하고 `USER_QUEST`, `ITEM`, `USER_ITEM` 변경을 한 트랜잭션으로 저장한다. 지급 실패 시 완료 기록도 롤백한다.
- 아이템은 미착용 상태로 지급한다. 동경이 꾸미기에서 착용하고 저장하면 `USER_ITEM.IS_EQUIPPED`에 반영된다.
- 프론트의 폭죽 화면 다음에 보상 창이 열린다. 손 아이템과 배경은 실제 아이템명도 표시한다.

보상 카탈로그는 `backend/db/quest_rewards.json`이다. `frontend/public/models/donggyeong/manifest.json`의 6개 역할·30개 에셋과 일치하는지 테스트한다. 화랑의 모델 ID는 `warrior_*`이다.

## API

세 API 모두 로그인 세션이 필요하다.

- `POST /api/v1/journey/quests/{questId}/complete`: 기존 완료 응답에 `reward`와 `inventory` 추가. 신규 지급이 없으면 `reward: null`.
- `GET /api/v1/donggyeong/inventory?persona=king`: 해당 역할의 보유 `items`와 착용 `outfit` 조회.
- `PUT /api/v1/donggyeong/outfit?persona=king`: `{"outfit":{"hat":"king_hat"}}` 저장. `{}`는 모두 해제. 보유하지 않은 아이템이나 잘못된 부위는 400 응답.

## 운영 반영 순서

1. Aiven CA 인증서를 준비하고 `.env`의 DB 접속/TLS 설정을 확인한다.
2. 새 백엔드 이미지에 포함된 마이그레이션을 실행한다: 저장소 루트에서 `docker compose build backend`, 이어서 `docker compose run --rm --no-deps backend alembic upgrade head`.
3. `0011`은 기존 ITEM 행을 보존하며 nullable `ITEM_CODE`와 고유 인덱스만 추가한다. 팀원의 스팟 번역 마이그레이션 `0010` 다음에 적용한다. 역할 아이템 마스터는 처음 지급될 때 등록된다.
4. 백엔드를 새 버전으로 실행한 뒤 프론트를 배포한다. `DB_AUTO_MIGRATE=false`이므로 실행만으로는 마이그레이션되지 않는다.
5. 운영 확인용 계정으로 새 퀘스트 완료 → 보유 아이템 조회 → 착용 저장 → 다시 로그인 순서로 확인한다.

자동 DB 테스트는 DROP/TRUNCATE를 사용하므로 운영 DB에서는 실행하지 않는다. 일회성 MySQL에서 전체 마이그레이션, 6개 역할의 지급 순서, 동시 요청, 롤백, API 소유권 검사와 재접속 조회를 검증한다.

## 운영 DB 검증 기록 (2026-09-20)

- Aiven CA를 통한 TLS 연결을 확인하고 `0010 → 0011`을 적용했다. 기존 아이템과 보유 기록은 보존했다.
- 임시 검증 계정으로 6개 역할의 보상 30종을 순서대로 지급했다. 같은 퀘스트 재요청과 여섯 번째 완료에서 추가 보상이 없음을 확인했다.
- 실제 API로 착용을 저장하고 새 DB 연결 및 조회 API에서 보유·착용 상태가 유지되는지 확인했다.
- 검증 계정과 해당 계정의 코스·퀘스트·보유 기록은 삭제했다. 역할별 아이템 마스터는 서비스에서 사용할 수 있도록 유지했다.
- 관련 백엔드 회귀 테스트 51개가 일회성 MySQL에서 통과했다. 로컬 Docker 백엔드는 운영 DB에 연결해 실행했다.
- 이 검증은 운영 DB와 로컬의 변경된 코드에 대한 것이다. Git 커밋·푸시 및 Vercel 재배포는 별도로 진행해야 한다.
